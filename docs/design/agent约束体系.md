# Agent 约束体系设计

> 本文描述仓库中**约束 agent 行为的那套机制**——它由哪些部件构成、各自解决什么问题、为什么这样组合。
>
> **职责分工**：[`CLAUDE.md`](../../CLAUDE.md) 只保留**可执行条文**（**何时做、做什么、怎么做、禁止什么**），**不写设计与原理**；**"为什么这么定"一律由本文承担**。两边刻意不重叠，以免同一件事被描述两处而后互相漂移。
>
> 本文与 `docs/design/` 下其它文档正交：那些文档描述 cross-relay-core 的**软件架构**，本文描述**协作流程的基础设施**。各域的产出各自成篇：[`docs/logs/`](../logs/index.md)、[`docs/pitfalls/`](../pitfalls/index.md)。

## 1. 要解决的问题

agent 是**无跨会话记忆**的：每次任务都是全新上下文，不知道上一轮改了什么、哪份文档已经过时、仓库里有哪些约定。仅靠"在对话里叮嘱"无法持久，因为对话本身不被下一轮继承。

因此约束必须**落在仓库里**、并在每轮任务的关键时刻被**重新注入**。这决定了整套机制的形态：一切约束都是文件，一切注入都靠 hook。

## 2. 三层结构

| 层 | 载体 | 解决的问题 | 生效时机 |
|---|---|---|---|
| **硬约束层** | `CLAUDE.md` | agent「必须怎么做」——行为准则、文档维护、日志维护、踩坑维护 | SessionStart + 每次 UserPromptSubmit，hook 直接 `cat` 进上下文 |
| **保鲜层** | `docs/meta.json` 的任务号 + 各域 `index.md` 的登记表 | 「哪份文档可能已过时」——把无记忆的 agent 引向需要复核的文档 | 任务号在 UserPromptSubmit 自增；agent 自行比对 |
| **检查层** | 各域 `scripts/check_index.sh` | 「agent 忘了怎么办」——兜底校验，把遗漏变成可见输出 | Stop hook，任务收尾时跑 |

三层的分工是**不重叠**的：硬约束层负责"告知"，保鲜层负责"定位"，检查层负责"兜底"。缺任何一层都会留下漏洞——只有硬约束而无检查，agent 漏做时无人发现；只有检查而无保鲜，agent 知道要检查却不知道该看哪几份。

## 3. 任务号：全流程的主线

`docs/meta.json` 只有一个字段 `taskorder`，由 `docs/scripts/increment_taskorder.sh` 在**每次 UserPromptSubmit 时自增**，并把新值注入上下文。

它是整个体系的**时钟**：agent 借助它知道"现在是第几轮"，文档借此记录"最后一次随任务更新是哪一轮"，检查脚本借此判断"谁落后了"。选择自增而非时间戳，是因为需要的语义是**因果序**（谁在谁之后更新）而非绝对时间——序号天然可比、可读、可写进文档表格。

该脚本属**跨域基础设施**，因此留在 `docs/scripts/`，而不归属任何单一域（见第 7 节）。

## 4. 文档域与索引表

每个文档域（如 `docs/design/`）有一个 `index.md`，用**机器可解析的表格**登记本域文档：

- **按列名取值，不依赖列顺序**——解析方（检查脚本）通过表头定位「文件地址」「taskorder」「只读」等列，因此表格列可以自由增减、调序；
- **`taskorder` 列 = 该文档最后一次被 agent 处理的任务号**。在 `docs/design/` 下，它的具体含义是「**本轮 agent 已复核该文档、并确认其与现有架构对齐**」的**凭证**——**不是**「内容最后一次被修改」的记录。因此每个非只读条目在**每轮任务结束时都必须等于当前任务号，即使内容一字未改**。agent 在任务开始时逐条复核：内容已过时则更新内容；但**无论改不改内容，复核完都要把登记值拨到当前任务号**。持续落后 = 该轮任务未完成，检查脚本会一直报；
- **`只读` 列**用于内容已稳定、不再演进的文档（如设计动机类）。标记为只读的文档**跳过保鲜校验**，但**仍参与索引对账**——它依然是一份必须被正确登记的文件。

这里的核心设计取舍是：**脚本只报不改**。`check_index.sh` 从不自动拨号——一旦自动，`taskorder` 就退化成橡皮图章，「agent 真的复核过」这个信号当场失真，字段本身也就没有存在价值了。**它唯一的价值恰恰在于"它可能没被更新"。**

**"报而不改"也不该退化成"给 agent 配个拨号工具"。** 本仓曾写过 `bump_taskorder.sh`（批量拨号、`--dry-run`、不接入 hook），用一轮就删了——因为它把"复核对齐"这个动作的摩擦降到接近零，于是必然被当作顺手一步执行。**它上线后第一次使用就橡皮图章了：4 篇从未打开过的文档被断言为"本轮已复核"。** 结论是：这里**只保留文本约束 + 手改**——摩擦本身就是信号的一部分，不该被优化掉（详见 [`docs/pitfalls/拨号工具会稀释断言信号.md`](../pitfalls/拨号工具会稀释断言信号.md)）。

## 5. 校验口径随文档生命周期而异

上节的保鲜规则隐含一个前提：**每轮任务都应该动这份文档**。这个前提只对"描述现状"的文档成立。文档实际上有三种生命周期，校验口径必须随之分化——**按生命周期选口径，而不是按文档格式**：

| 生命周期 | 域 | 内容性质 | `taskorder` 语义 | 触发条件 | 校验口径 |
|---|---|---|---|---|---|
| **保鲜型** | `docs/design/` | 对现状的描述，现状变了就该重写 | **本轮已复核并对齐**的凭证 | **每轮必做** | 逐行 == 当前（只读条目豁免） |
| **追加型** | `docs/logs/` | 历史事实的记录，一旦写下不再改变 | 该文件**最新一次被写入**的任务号 | 本轮产出了日志才做 | **只校验倒排首行**；历史行完全不校验 |
| **非强制型** | `docs/pitfalls/` | 偶发记录，大多数任务不产生 | 踩坑**发生**时的任务号，仅供追溯 | 偶发 | **完全不校验** |

三者其实**同源**：`taskorder` 都是「该文档**最后一次被 agent 处理**的任务号」。分化的是**触发条件**——design 每轮必被"处理"（复核），logs 只在产出日志时被"处理"（写入），pitfalls 只在踩坑时被"处理"（记录）。**触发条件不同，就该用不同的校验口径**，而不是给三者套同一条规则。

因此关键是把**列**和**校验规则**解耦：`taskorder` 列在各域都保留，但"列存在"不等于"必须被校验"，更不等于"每轮都必须更新"。

> 上表是**机理**视角（为什么这样分化）。各域**具体填什么值**属于可执行条文，只在 [`CLAUDE.md`](../../CLAUDE.md) 的「任务号（taskorder）」节里定义一处，本文不复刻。
>
> 那个条文表里最需要留心的是：design 与 logs 的值**碰巧相同**（都是当前任务号），极易让人形成"`taskorder` 就是填当前值"的直觉；而 **pitfalls 填的是踩坑发生时的任务号，可能是过去值**——它是同名列里唯一不代表"本轮处理"的一个。**两个域巧合一致，第三个不同**，这种"多数一致"正是最容易被归纳错的形状。

### 5.1 日志域：两处刻意偏离

- **倒排索引**——最新完成的日志排在表格**最前**。文档索引按主题排，日志索引按时间排，因为查询日志的典型意图是"最近发生了什么"。
- **只校验首行**——倒排首行即最新一篇日志，其 `taskorder` 必须等于当前任务号。由此派生出**合并语义**：主题相似的多次任务写进同一篇日志（追加小节，而非另开文件）时，agent 需把被复用那一行的 `taskorder` **拨到当前任务号**并保持其在表格最前——该行被多个任务共用，其中最新共用的任务即当前任务。同一文件因此有**多个归属任务号**，而索引只记录最新的那个。

日志正文的固定结构（原需求 / 计划 / 实做 / 问题 / 解法 / 完成时间）同样是约束：它强制 agent 记录**走过的弯路**，而不只是结论——这类信息在代码与提交历史里都留不下来。

### 5.2 踩坑域：不设强制校验

踩坑记录**不是每轮任务都有**。若同样要求"首行必须由当前任务产生"，agent 为了通过检查就只能**凑数**——凭空制造几条无价值的条目，反而稀释本目录的价值。因此这里**取消一切 `taskorder` 校验**，只保留索引↔磁盘对账（保证"记了坑就必须登记"这一最低一致性）。

与日志的另一处差异是**文件命名**：踩坑记录用**主题命名、不带时间戳**（如 `文件名冒号在macOS的坑.md`）。日志是流水账，时间戳是它的主键；踩坑是知识条目，**同一类坑反复踩到时应归并进同一篇**——带时间戳反而会把它拆成互不相干的碎片。

这一节的结论值得单独记住：**"为通过检查而凑数"是任何强制指标的通病**。设指标时必须问一句：这个东西是否每轮都该有？若不是，就不要设。

## 6. 脚本按域分离

检查脚本的部署方式是**每个域自带一份**：

```
docs/scripts/increment_taskorder.sh        # 跨域基础设施：全局任务号自增
docs/design/scripts/check_index.sh         # hook 脚本：只管 docs/design/
docs/logs/scripts/check_index.sh           # hook 脚本：只管 docs/logs/
docs/pitfalls/scripts/check_index.sh       # hook 脚本：只管 docs/pitfalls/
```

**四份脚本全是 hook 脚本**，没有例外——不存在"供 agent 手动调用"的工具脚本。设计域的 taskorder 拨号是纯手改，刻意不配工具（见第 4 节末）。这条边界要守住：一旦有人为了方便再加一个 `bump_*.sh`，就等于把第 4 节那次的教训重演一遍。

关键约定：**域根由脚本自身路径推导**（脚本上一级即域根），而非硬编码目录。这样扫描范围天然互斥——一个域新增或删除，不影响另一个域；也不需要任何"排除某目录"的补丁（历史上曾用硬编码排除 `docs/logs/` 来规避误报，正是被这一设计取代的）。

代价是三个脚本的**表格解析代码各有一份**。这是**有意为之**：抽公共库会让刚解耦的域重新通过库耦合，改库就得回归所有域。此处重复换来的独立性更值。新增域时照抄一份、改路径与校验口径即可。

## 7. Hook 挂载表

约束注入与检查全部挂在 `.claude/settings.local.json` 上：

| 事件 | 动作 | 作用 |
|---|---|---|
| **SessionStart** | `cat CLAUDE.md` | 会话启动即注入硬约束，避免 agent 在无约束状态下开始 |
| **UserPromptSubmit** | `cat CLAUDE.md` | 每次提问前重申硬约束 |
| **UserPromptSubmit** | `bash docs/scripts/increment_taskorder.sh` | 自增并注入任务号，同时提醒复核各域索引 |
| **Stop** | `bash docs/design/scripts/check_index.sh` | design 域：逐行保鲜校验 + 索引↔磁盘对账 |
| **Stop** | `bash docs/logs/scripts/check_index.sh` | logs 域：首行 taskorder 校验 + 索引↔磁盘对账 |
| **Stop** | `bash docs/pitfalls/scripts/check_index.sh` | pitfalls 域：**仅**索引↔磁盘对账 |

两次 `cat CLAUDE.md` 是**刻意冗余**：SessionStart 覆盖"新会话"，UserPromptSubmit 覆盖"长会话中上下文被压缩后约束被挤出"的情形。约束被遗忘的代价远高于重复注入的成本。

**索引↔磁盘双向对账**是检查层的通用能力（三个域都有）：磁盘有 `.md` 而未登记（缺少索引）、登记了而无文件（多余索引）都会报出。它兜住的是 agent 最容易犯的错——新增了文档却忘了登记。

## 8. 已知边界

- **保鲜检查无法判断内容对错**，只能提示"落后"。真正的复核依赖 agent 阅读文档与本次任务的关联，这是一处**有意保留的人工环节**。
- **脚本自身不校验自身**：`check_index.sh` 的正确性没有自动化保障，改动后需人工以无副作用方式验证（`bash -n`、独立复现解析逻辑等）。按 [`CLAUDE.md`](../../CLAUDE.md) 的规定，这些 hook 脚本**禁止手动执行**——因为它们会产生多余的任务号自增与检查输出，污染真实流程。
- **校验口径的差异会长期存在**：三个域的检查脚本并不一致，且不应被"统一"。抹平差异就等于把某种生命周期硬套到不适用它的域上（见第 5 节）。
- **`logs/` 与 `docs/logs/` 是两个东西**：仓库根 `logs/` 是运行时日志目录（已在 `.gitignore` 中以锚定形式 `/logs/` 忽略），agent 任务日志则一律写 `docs/logs/`。锚定不可省略——无前导斜杠的 `logs/` 会匹配任意层级，连带忽略 `docs/logs/`。
