## 1. 项目定位

cross-relay-core 是内网穿透项目 cross-relay 的核心库，基于 Java Netty 实现，提供客户端与服务端的通用中继逻辑。整体模型为**双层中继**：

- **服务端**（公网机器）：对外暴露 requester 端口接收外部用户访问，对内暴露 client-proxy 端口接收内网客户端的回连；
- **客户端**（内网机器）：代理本地内网服务，收到服务端指令后回连服务端并连向真实服务，把数据流在两端之间搬运。

核心架构分两部分：

1. **Control（通信控制器）**：客户端与服务端之间的加密控制通道，负责握手认证、心跳保活、身份信息交换，以及隧道调度类控制事件（如 `REQUIRE_CHANNEL`）的传递；
2. **Proxy（代理器）**：真正的数据面，负责建立和维持隧道（Tunnel）、转发业务字节流。Proxy **依赖 Control** —— 隧道的建立指令、关闭通知都经由 Control 通道下发，但业务数据走独立的 Proxy 通道（明文，不加密）。

> **为什么是双层中继？** 在最严格的 NAT 下，内网端口必须主动请求外部才对外可达，而已绑定 8080 的本地服务无法自救——因此需要本地另起端口运行中继客户端（ProxyClient）主动连接公网服务器，由服务器（ProxyServer）提供公网端口供外部请求者访问，流量经服务器中继转交内网真实服务。当前刻意采用这一最保守策略以获得最大可用性、稳定性与通用性；针对更宽松 NAT 的特制优化策略在计划中。详见 [prime-design.md](./prime-design.md)。

### 模块总览

```
top.fateironist.cross_relay_core
├── Client / Server / Listener          顶层生命周期接口与标记接口
├── ClientStatus / ServerStatus         状态机枚举
├── DefaultEventLoopGroup               共享 Future 工具 + 内部定时任务的线程组（非组件 IO 线程组）
├── control/                            通信控制器
│   ├── ControlClient / ControlServer   控制通道两端（Netty）
│   ├── ServerInfoServer                UDP 元数据查询应答服务（端口 3461）
│   ├── handler/                        EventEncryptHandler、IdleEventHandler、JsonEncoder/Decoder
│   └── listener/                       ControlClientListener、ControlServerListener（钩子）
├── proxy/                              代理器（数据面）
│   ├── ProxyServer / ProxyClient       TCP+UDP 聚合门面
│   ├── ProxyTcpServer / ProxyTcpClient TCP 实现
│   ├── ProxyUdpServer / ProxyUdpClient UDP 实现
│   └── listener/                       ProxyServerListener、ProxyClientListener（钩子）
├── manager/                            ProxyManager（隧道管理接口）
├── model/
│   ├── control/                        ControlContext、ControlEvent、事件枚举
│   ├── proxy/                          ProxyContext/TunnelContext 体系
│   ├── info/                           ProxyClientInfo、ProxyServerInfo、ClientServiceInfo 等
│   └── args/                           各组件启动/连接参数（含 Options Builder）
└── util/                               EncryptUtil（RSA+AES）、JsonUtil、SynchronizedWeakHashSet
```

> **DefaultEventLoopGroup 澄清**：共享的是它的 Future 工具（`newPromise`/`emptyFuture`/`failFuture`/`combine`）与内部定时任务（如 `ServerUdpProxyContext` 的超时扫描）所在的线程组，**不是**各组件的 IO 线程组——control 与 proxy 各组件的 EventLoopGroup 均由上层注入（见 `DefaultEventLoopGroup` 类头注释）。

**一条贯穿全局的设计原则**：一切核心功能留在核心库，绝不委托给上层实现。握手、认证调度、通道建立的编排与配对、隧道状态机一律内聚在 core 的类（ControlContext、ProxyContext、TunnelContext 体系）中；listener 系列类被弱化为**通知**（`onTunnelEstablished`/`onTunnelClose` 等生命周期告知）与**业务 event 处理**（`addEventHandler` 注册的自定义事件）两种纯粹角色，业务层不承担任何核心逻辑。

## 2. Control 通信控制器

### 2.1 角色定位

| 类 | 端 | 职责 |
|---|---|---|
| `ControlServer` | 服务端 | 监听控制端口（默认 3416），管理所有客户端控制会话 |
| `ControlClient` | 客户端 | 连接服务端控制端口，维持唯一控制连接 |
| `ServerInfoServer` | 服务端 | UDP 服务（固定端口 3461），**应答 `SERVER_INFO` 查询（单播）**，回本机 `ProxyServerInfo`（control/proxyRequest/infoServer 三个地址） |

职责边界：control 承担加密通道、身份信息传递，以及通道建立类控制事件（REQUIRE_CHANNEL 等）的拦截与转发。

Pipeline（两端对称，见 `ControlServer` / `ControlClient` 的 pipeline 装配段）：

```
IdleStateHandler(pingTimeout) → IdleEventHandler → 长度域解码/编码
→ EventEncryptHandler(AES-GCM) → JsonEncoder/JsonDecoder → 业务 Handler
```

> 握手的完整时序（RSA-2048/OAEP 密钥交换 → AES-256-GCM 会话加密 → `beforePermit` 认证 → CONNECTION_PERMIT → PING/PONG 保活）与逐条说明见 [control 建立流程](./control建立流程.md)。

### 2.2 事件体系

`ControlEventEnum` 为接口，两个实现枚举。

**ControlProtocolEventEnum**（协议/握手层）：

| 事件 | 流向 | 说明 |
|---|---|---|
| `SESSION_PUBLIC_KEY` | 客户端→服务端 | RSA 公钥，明文 |
| `SESSION_SECRET_KEY` | 服务端→客户端 | RSA 加密的 AES 会话密钥 |
| `SESSION_SECRET_ACK` | 客户端→服务端 | body 为 `ProxyClientInfo`（身份上报） |
| `CONNECTION_PERMIT` | 服务端→客户端 | 认证通过，携带 controlId 与 ProxyServerInfo |
| `ERROR` | 服务端→客户端 | 拒绝/异常，body 为 `Error` |
| `PING` / `PONG` | 客户端⇄服务端 | 心跳与 RTT 测量 |
| `SERVER_INFO` | UDP 查询 | 客户端向 ServerInfoServer 查询服务端元数据 |
| `CLOSE` | 双向 | `ControlContext.closeRemote()` 主动通知对端关闭 |
| `ACK` / `CLIENT_INFO` | — | 定义了但 main 中未使用（预留） |

**ProxyControlEventEnum**（代理业务层）：

| 事件 | 流向 | 发送点 |
|---|---|---|
| `REQUIRE_CHANNEL` | 服务端→客户端 | 服务端 `ServerProxyContext.requireChannel()` 经 control 通道发出；客户端侧的拦截驱动逻辑**尚未实现**（枚举已预留，原计划经 listener 的 `addEventHandler` handler 实现，见 §6 已知问题） |
| `TUNNEL_CLOSE` | 双向 | `ProxyContext.closeRemoteTunnel()` |
| `PROXY_CLOSE` | 双向 | `ProxyContext.closeRemoteProxy()` |
| `REGISTER_PROXY` / `REGISTER_PROXY_ACK` | 客户端⇄服务端 | **库内无发送点**，由上层业务通过 listener 的 `addEventHandler` 注册实现 |

事件信封 `ControlEvent<T>`：`id`（AtomicLong 递增）/`ack`/`type`/`body`。`ack` 为**纯占位字段，收发双方尚未消费**（仅 `ControlEvent(Long ack)` 构造器会设置）。proxy 业务事件的 body 载体为 `CommonInfo{tunnelId, proxyId, protocol}`。

### 2.3 ControlListener 钩子

两个 listener 均为**类**（覆写 + `addEventHandler` 注册表分发，`onEvent` 为 final），默认空实现/放行：

**ControlServerListener**：

| 钩子 | 触发时机 | 默认行为 |
|---|---|---|
| `beforeAccept(channel)` | TCP accept 过滤（可做 IP 黑名单） | return true |
| `afterAccept(context)` | channelActive，已分配 controlId | 空 |
| `beforePermit(context, event)` | 加密完成后身份认证 | return true（false 则回 ERROR 关闭） |
| `onEvent(context, event)` | permit 后的业务事件（按 addEventHandler 分发） | 空 |
| `caughtException(context, t)` | exceptionCaught | 空 |
| `onTimeOut(context)` | READER_IDLE 超时 | `context.close()` |
| `onClose(context)` | channelInactive | 空 |

**ControlClientListener**：`afterPermit`（收到 CONNECTION_PERMIT 后，即握手完成点，通常在此启动 proxy 层）、`onDeny`、`onEvent`、`caughtException`、`onTimeOut`（默认 close）、`onClose`、`addEventHandler`。注意 `onDeny` 仅覆盖「已加密、未 permit」阶段（见 [control 建立流程](./control建立流程.md) §6）。

### 2.4 关键数据结构

- **ControlContext**（`model/control/ControlContext.java`）：挂在 channel attr 上的会话上下文。字段：`controlId`（`CTL-<uuid>`）、双向合并的 `proxyClientInfo`/`proxyServerInfo`、`channel`、ping 调度器、`msgId`（AtomicLong）、`permit`/`encrypted` 状态位、异常容忍计数（`handleAbnormalEvent()` 计数**超过容忍上限（> `maxTolerableAbnormalEventCount`=5）即关闭**）、`closeHook`（服务端用于从会话表移除）。`close()` = 发 CLOSE + 取消 ping + hook + 关 channel。
- **ProxyServerInfo**（`model/info/ProxyServerInfo.java`）：服务端三地址（control / proxyRequest / infoServer），提供单机/分布式工厂、`receivePong` 延迟统计、`getMetaDataFromServerInfoServer()` UDP 发现（客户端连接 control 前先经此寻址）。
- **ProxyClientInfo**（`model/info/ProxyClientInfo.java`）：客户端身份（id/凭证/地址），`setAdditional` 做字段级合并。
- **ClientServiceInfo**（`model/info/ClientServiceInfo.java`）：内网服务描述，`checkAddress()` 强制回环/本地地址。
- **args/options**：`ControlServerStartArgs`（port=3416、maxConnections=128、pingTimeout=30000）、`ControlClientConnectAbstractArgs`（pingInterval=5000、**pingTimeout=30000**）等，均以 `Function<OptionsBuilder, OptionsBuilder>` lambda 定制默认值。
- **ServerInfoServerStartArgs**：其 Options **不含任何端口字段**，UDP 3461 端口是 `ServerInfoServer.PORT` 硬编码。

## 3. Proxy 代理器

### 3.1 角色定位

Proxy 按端 × 协议分为 4 个实现，外加 2 个聚合门面：

| 类 | 端 | 协议 | 监听/连接 |
|---|---|---|---|
| `ProxyTcpServer` | 服务端 | TCP | 两类 ServerBootstrap：**client-proxy 端口**（默认 3418，收客户端回连，**全局仅一个、所有客户端共享**）+ **requester 端口**（`bind(0)` 随机，收外部用户，**每个 ProxyContext 一个、一一对应**） |
| `ProxyTcpClient` | 客户端 | TCP | 每条隧道建两条连接：连内网服务（serviceProxyBootstrap）+ 连服务端 requester 端口（serverConnecterBootstrap） |
| `ProxyUdpServer` | 服务端 | UDP | 两条 `NioDatagramChannel`：client-proxy 端（**全局仅一条、所有客户端共享**）+ requester 端（`bind(0)`，**每个 ProxyContext 一条、一一对应**），channel 多连接复用，按 `InetSocketAddress` 区分对端 |
| `ProxyUdpClient` | 客户端 | UDP | **单条 duplex channel**，既连内网服务又通服务端，首包即 JSON 注册包 |
| `ProxyServer` | 服务端 | — | 聚合门面，按 Options 的 `enableProxyTcp/enableProxyUdp` 启停子服务器 |
| `ProxyClient` | 客户端 | — | 聚合门面，按 `ProxyClientConnectArgs.protocol` 二选一 |

**状态机**：各**子实现**（ProxyTcpServer/ProxyTcpClient/ProxyUdpServer/ProxyUdpClient 及 control 两端）均有 `INIT→RUNNING/OPEN→CLOSING/CLOSED→SHUTDOWN` 状态机（`ServerStatus`/`ClientStatus` volatile 字段）；`ProxyServer`/`ProxyClient` 两个聚合门面**不持有状态、不做状态门控**，直接转发子实现。

### 3.2 ProxyContext / TunnelContext 体系

**ProxyContext**（抽象基类，`model/proxy/ProxyContext.java`）— 一个 proxyId 对应一个，跨隧道复用。**通道建立的核心逻辑即委托在这一层**：proxy 级的注册（`tunnelRegisterMap`）、对 control 通道的控制事件收发、以及隧道生命周期的编排都内聚于此；

- `KEY` AttributeKey 绑定 channel，pipeline 可反查；
- `proxyId`（`PXY-UUID`）、`controlContext`（**对 control 的依赖点**，控制事件经它回写）、`tunnelRegisterMap`（tunnelId → TunnelContext）、`closeProxyHook`；
- 关键方法：`newTunnelContext()` / `newTunnelContext(tunnelId)`（挂 `tunnelCloseHook` 出 map + `closeRemoteTunnelHook` 发 TUNNEL_CLOSE，随后入 map）、`close()`（逐 tunnel 优雅关闭 + 发 `PROXY_CLOSE` + 逐 channel 关闭）、`controlClient(event)`。

继承结构：

```
ProxyContext
├── ClientProxyContext（标记基类）
│   ├── ClientTcpProxyContext
│   └── ClientUdpProxyContext       + addressContextMap（地址→tunnel，见 UDP 文档"已知问题"：尚未接线）
└── ServerProxyContext              + requesterWaitMap + requireChannel()
    ├── ServerTcpProxyContext       + registerRequester/registerClientProxy（Channel 版）
    └── ServerUdpProxyContext       + 地址版注册 + 10s 周期超时定时器
```

**TunnelContext**（`model/proxy/tunnel/`）— 一条隧道一个，一次性。隧道级建立状态机也委托在这层：两端 channel/address 的配对、`tryOpen()` 判定 OPEN、`closeGracefully` 级联关闭与对端通知：

- 基类字段：`tunnelId`（`TUN-UUID`）、`status`（INIT/OPEN/CLOSING/CLOSED）、`tunnelCloseHook`/`closeRemoteTunnelHook`；`closeGracefully()`（hook + 通知对端 `TUNNEL_CLOSE`）、`closeLocal()`（仅本地）、抽象 `tryOpen()`（两端 channel 齐备即 OPEN）；
- `ClientTcpTunnelContext`：serviceChannel + clientProxyChannel；
- `ServerTcpTunnelContext`：requesterChannel + clientProxyChannel；
- `ClientUdpTunnelContext`：单 duplexChannel + serviceAddress + serverProxyAddress，`writeToOpposite(sender,msg)` 按来源双向转发，30s 无活动超时；
- `ServerUdpTunnelContext`：requester 与 clientProxy 的 channel/address 四元组，`DatagramPacket(msg.retain(), address)` 转发，同样 30s 超时。

### 3.3 ProxyListener 钩子

均为普通类（默认空实现/放行），供上层观测与准入控制：

**ProxyServerListener**：

| 钩子 | 触发时机 | 默认 |
|---|---|---|
| `beforeClientToServerConnectionAccept` | 客户端回连到达 client-proxy 端口（仅 TCP） | true |
| `beforeRequesterToServerConnectionAccept` | 外部 requester 连接/数据包到达 | true |
| `onTunnelEstablished` | **注册配对成功、tunnel 必然 OPEN 时**：TCP 服务端在 client-proxy 注册包配对成功处（`ProxyTcpServer` client-proxy handler），UDP 服务端在 `registerClientProxy` 配对成功处；客户端 TCP 在虚拟线程双连接 sync 完成后（`ProxyTcpClient.connect` 末尾，单次） | 空 |
| `onTunnelClose` | 隧道关闭（TCP requester channelInactive；客户端 service channelInactive 等） | 空 |
| `caughtTunnelException` | 各端 exceptionCaught | 空 |

**ProxyClientListener**：`onTunnelEstablished` / `onTunnelClose` / `caughtTunnelException`（调用点见各引导类；UDP 客户端 `ProxyUdpClient` 仍在 channelActive 与 `connect()` 末尾各回调一次，见 UDP 文档已知问题）。

### 3.4 数据面 handler 链与安全边界

- **TCP proxy pipeline 极简**：childPipeline 仅一个 `SimpleChannelInboundHandler<ByteBuf>`，无编解码、无加密。channel 接入分两侧：**requester 侧父 handler** 在建隧道时直接写入 `TunnelContext.KEY` attr；**client-proxy 侧**连接到达时 attr 为空，靠**首包 JSON 注册包**按 proxyId 定位上下文、配对成功后再绑定 attr。注册 JSON 包假设一次性整包到达（一次性 `readString`），**无粘包处理**。
- **UDP**：单 `NioDatagramChannel` + `SimpleChannelInboundHandler<DatagramPacket>`；requester 端曾配置的 `IdleStateHandler(0,0,requesterTimeout)` 因无 `IdleEventHandler` 消费而无效，已注释。
- **安全边界**：仅 control 通道加密（AES-256-GCM）；**所有业务数据流为明文**，proxy pipeline 中无 `EventEncryptHandler`。
- **util**：`EncryptUtil`（RSA-2048/OAEP + AES-256-GCM）、`JsonUtil`（共享 ObjectMapper）、`SynchronizedWeakHashSet`。

## 4. 三大通道（流程索引）

本项目的数据通路由三类通道构成，各自的**建立流程**分篇展开：

| 通道 | 文档 | 本文档中的对应结构 |
|---|---|---|
| control 通道（加密，控制面） | [control 建立流程](./control建立流程.md) | §2 Control 通信控制器 |
| TCP 通道（明文，面向连接） | [TCP 通道建立流程](./TCP通道建立流程.md) | §3 Proxy 代理器 · TCP 实现 |
| UDP 通道（明文，无连接） | [UDP 通道建立流程](./UDP通道建立流程.md) | §3 Proxy 代理器 · UDP 实现 |

三篇文档共享同一套结构不变量，理解这三点即可把握流程全貌：

1. **控制面调用点单向收敛**：引导类（`ProxyTcpServer/Client`、`ProxyUdpServer/Client`）**不直接触碰 control 通道**，与 control 的全部交互都内聚在 ProxyContext 体系内，路径统一为 `ProxyContext.controlClient(event)` → `ControlContext.writeAndFlush()`（附加递增 msgId）→ 加密 control 通道；control 事件的内容构造（`CommonInfo{tunnelId, proxyId, protocol}`）只存在于 ProxyContext 内部。
2. **控制面发起、数据面闭环**：服务端 requester 到达 → `registerRequester()` 挂 Promise 入 `requesterWaitMap` → 经 control 通道发 `REQUIRE_CHANNEL` → 客户端在**数据面通道**上以注册包回应 → 服务端 `registerClientProxy()` 完成 Promise、`tryOpen()` 置 OPEN。TCP 与 UDP 完全同构。
3. **关闭路径对称**：tunnel 的 `closeGracefully()` 在两端都通过同一个 `closeRemoteTunnelHook` 通知对端（`TUNNEL_CLOSE`），使 requester 断开、内网服务断开、UDP 超时等本端触发点都能级联到对端；`ProxyContext.close()` 下线时逐 tunnel 优雅关闭并发 `PROXY_CLOSE`。**注意：TCP/UDP 的 client-proxy 中继段两端断开目前仅记日志、不触发级联**（UDP 客户端 duplex channel 的 `TunnelContext.KEY` 已补挂，该侧级联恢复有效）。

### 通道分离总结

| 通道 | 端口 | 加密 | 协议 | 承载内容 |
|---|---|---|---|---|
| control 通道 | 3416 | AES-256-GCM | 长度前缀 + JSON `ControlEvent` | 握手、心跳、隧道调度事件 |
| proxy requester 通道 | 随机(bind 0) | 明文 | TCP 裸流 / UDP | 外部用户 ⇄ 服务端 |
| proxy client-proxy 通道 | 3418 | 明文 | TCP 裸流 / UDP | 客户端回连 + 首包 JSON 注册 |
| info server | 3461 (UDP) | 明文 | JSON | 服务端元数据发现 |

## 5. 服务间依赖关系

```
        上层业务应用（实现各 Listener 钩子：准入过滤、观测、认证；不参与通道建立编排）
                 │                              │
        覆写钩子 │                              │ 注册业务事件 handler
                 ▼                              ▼
   ┌───────────────────────────┐   ┌────────────────────────────┐
   │    Proxy 层（数据面）      │   │    Control 层（控制面）     │
   │ ProxyServer/ProxyClient   │   │ ControlServer/ControlClient│
   │  ├─ ProxyTcpServer/Client │   │ ServerInfoServer (UDP 3461)│
   │  └─ ProxyUdpServer/Client │   │                            │
   │ ProxyContext/TunnelContext│◀──┘ ControlContext/ControlEvent│
   └───────────┬───────────────┘      （通道建立指令在此拦截）   │
               │ 持有 ControlContext            ▲              │
               └── REQUIRE_CHANNEL / TUNNEL_CLOSE / PROXY_CLOSE ─┘
                            （控制事件走加密 control 通道）
```

依赖要点：

1. **proxy → control（单向依赖）**：proxy 的启动参数直接携带 `ControlContext`（`ProxyClientConnectArgs`、`RequesterProxyServerStartArgs`）；`ProxyContext.controlClient()` 通过它发送 `REQUIRE_CHANNEL`/`TUNNEL_CLOSE`/`PROXY_CLOSE`。control 自身不感知 proxy。
2. **通道建立由核心全权负责，业务层不参与编排**：服务端隧道挂起 → `ServerProxyContext.requireChannel()` 经 control 通道发出 `REQUIRE_CHANNEL` → 客户端核心在 control 通道上拦截该指令 → 核心内部（TunnelContext/ProxyContext 体系）驱动 `ProxyTcpClient/ProxyUdpClient` 完成双连接建立与注册配对。上层仅通过 Listener 钩子（准入过滤、`onTunnelEstablished`/`onTunnelClose` 等观测点）介入。
3. **寻址依赖**：客户端连接 control 前需获得 `ProxyServerInfo`（control 与 proxyRequest 地址）。获取渠道不限于库内能力：库内仅提供 UDP 发现（`ServerInfoServer`，UDP 3461）作为**备选**，当前无实际代码调用；未来还会经 HTTP 端点、社交媒体等渠道暴露服务端信息。
4. **manager 层**：`ProxyManager`（`manager/ProxyManager.java`）声明 `closeTunnel(tunnelId)` 接口，供上层关闭指定隧道（对应 `TUNNEL_CLOSE` 事件）；control 侧不设 manager，control 的扩展点只有 Listener（一切核心功能留在核心库，见 `ControlClient`/`ControlServer` 类头注释）。

## 6. 已知问题与待完善（源码中标注）

- **粘包风险**：TCP 注册包一次性 `readString` 假设整包到达，无拆包 handler（`ProxyTcpServer` / `ProxyUdpServer` 注册解析处同此假设）。
- **`OriginalRequesterInfo` 构造器 bug**：构造器形参被整体丢弃（`this.address = address; this.protocol = protocol;` 字段自赋值），`address` 与 `protocol` **两个成员字段均恒为 null**。
- **`DefaultEventLoopGroup.combine()` 缺陷**：在 eventLoop 任务中先 `setSuccess` 后 `f.get()`，成功路径立即完成、异常路径 setFailure 无效。
- **UDP channel 复用**：`ProxyUdpServer` 多处 `// fixme` 标注多连接复用同一 channel 的处理待完善；两条共享 channel 的 `exceptionCaught` 直接 `ctx.close()`，单个客户端异常会中断该 channel 上所有客户端。
- **骨架未完成**：`ProxyManager` 仅接口声明；`REGISTER_PROXY(_ACK)`、`ACK`/`CLIENT_INFO` 事件无 main 源码收发点；**客户端拦截 `REQUIRE_CHANNEL` 的驱动逻辑尚未实现**（枚举已预留，三篇流程文档中的"客户端核心拦截"为目标设计）。
- **客户端 `addressContextMap` 未接线（UDP）**：`ClientUdpProxyContext` 的地址版 `newTunnelContext(tunnelId, address)` 重载已补挂双钩子，但 `ProxyUdpClient` 实际调用的是基类单参 `newTunnelContext(String)`，地址表永不填充——详见 UDP 文档"已知问题"。
- **UDP 注册失败无客户端感知**：服务端注册失败已回滚会话表并 return（不再 NPE/脏路由），但仅打日志不回应，客户端仍无失败感知。

已在本轮修复（留档）：`ProxyServer.start()` 的局部变量遮蔽/null 返回/TCP 失败不回收 UDP；`ServerUdpTunnelContext` setter 条件笔误；`ClientUdpProxyContext` 地址版重载缺 `closeRemoteTunnelHook`；`ServerUdpProxyContext.registerRequester` 判空；`ProxyUdpClient.channelActive` 补挂 `TunnelContext.KEY`；`onTunnelEstablished` 两端语义已对齐为「配对成功、必然 OPEN」（服务端移到注册配对成功后触发）。
