# Prime Design：为什么选择双层中继架构

> 本文阐述 cross-relay-core 最核心的设计决策——为何采用"本地客户端代理本地服务、服务器代理本地客户端"的双层中继模型，以及该模型背后的 NAT 穿透原理与未来演进方向。

## 1. 问题的本质：最严格 NAT 下的可达性约束

NAT（网络地址转换）设备对入站流量的容忍度各不相同，可以按严格程度排列成一个谱系：

- **最严格的 NAT**（对称型 / 端口受限型）：外部若想请求内网的某个端口，该端口必须**曾以同一端口**主动向外部发起过请求。也就是说，内网端口与外部可达性被严格绑定，外部几乎无法主动触碰任何未被"预订"的端口。
- **较宽松的 NAT**（如完全锥形等）：外部想请求内网的某个端口，只要求该内网 IP **曾以任意端口**主动请求过外部即可，无需强制端口一一对应。

穿透的目标场景是：内网中运行着一个真实服务（例如监听 `localhost:8080` 的 Web 应用），我们希望公网上的任意外部请求者都能访问到它。

## 2. 双层结构的推导

以最严格的 NAT 为约束条件，可以一步步推导出当前架构：

### 2.1 内网必须主动发起连接，而 8080 无法自救

在最严格的 NAT 下，任何从外部主动发往内网的流量都会被丢弃。因此**穿透的发起方向必须是"内网 → 外网"**——内网必须自己主动请求外部，才能为后续的双向数据打开一条通道。

但矛盾在于：本地服务已经绑定在 8080 端口上对外提供服务语义，我们不可能（也不应该）让 8080 端口自己去向公网发起请求。**8080 端口自身无法完成穿透**。

### 2.2 第一层：本地中继客户端（本地服务 → 内网代理）

结论是必须在本地**另起一个端口**，由一个独立进程主动向外部发起连接——这就是**本地中继客户端**（ProxyClient）：

- 它与本地服务处于同一内网，通过本地回环/局域网地址连接真实服务（`ClientServiceInfo.checkAddress()` 强制要求回环或本地地址，正是为了保证这一层不跨越不可信网络）；
- 它主动向公网服务器发起连接，从而在 NAT 上"预订"了可达性；
- 它充当本地服务的代理：所有需要送达 8080 的流量，都由它代为接收并转交。

### 2.3 第二层：公网中继服务器（本地客户端 → 外部请求者）

本地客户端主动连接的对面，就是部署在公网上的**中继服务器**（ProxyServer）。服务器为客户端提供公网可达的 IP 与端口（requester 端口），于是完整链路形成：

```
外部请求者 ──▶ 服务器公网端口（requester）
                 │
                 ▼
            公网中继服务器（数据在此中转）
                 │
                 ▼
           本地中继客户端（主动连接，NAT 可达）
                 │
                 ▼
            内网真实服务（如 localhost:8080）
```

外部请求者请求服务器的公网端口，流量经服务器中继，最终由内网代理转交到真实服务；响应原路返回。这就是"客户端代理本地服务、服务器代理本地客户端"的**双层中继**。

## 3. 设计取舍：为什么当前只实现最保守的方案

需要明确的是，双层中继并非穿透的唯一解，而是**针对最严格 NAT 的通用解**：

- 它不依赖对 NAT 类型的探测，也不依赖 NAT 的宽松特性——只要内网能主动出站（几乎所有 NAT 都允许），链路就能建立；
- 因此它具备**最大的可用性、稳定性与通用性**：同一条链路在最严格 NAT 下可行，则在一切更宽松的 NAT 下必然可行。

代价是性能：所有流量都必须绕经公网服务器中转（两跳），且本地客户端需为每条隧道维护额外连接。对宽松 NAT 环境，这本可以走更短的路径或更轻的通道。

## 4. 未来演进方向

当前实现刻意保持单一、保守的穿透策略。后续计划引入**针对更宽松 NAT 的特制策略**：

- 对可判定为宽松 NAT（如完全锥形）的场景，利用"内网 IP 曾主动出站即可从任意端口入站"的特性，减少中继跳数或复用通道；
- 从而在保证可用性兜底（最严格 NAT 仍走双层中继）的前提下，优化宽松 NAT 环境下的转发性能。

换言之，双层中继是本项目的**基线通路（prime path）**，未来更激进的策略都是在这条基线之上的优化分支，而非替代。
