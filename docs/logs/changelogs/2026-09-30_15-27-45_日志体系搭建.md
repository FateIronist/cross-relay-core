## 一、用户原需求

以与 `docs/` 相同的方式组织 `logs`：`logs` 下分为 `index.md` 与 `changelogs` 文件夹；agent 的日志文件全部记录在 `changelogs` 下；日志正文需说明——

- 本次任务用户原需求
- 简要计划
- 实际做了什么
- 遇到了什么问题
- 如何解决的
- 任务完成时间

日志文件以 `yyyy-mm-dd_hh:mm:ss+主题` 命名；多次任务若主题相似可合并到同一文件；`logs/index.md` 比较特殊，采用**倒排**（最新的日志放到索引最前面）。

## 二、简要计划

1. 先探明 `docs/` 侧「相同的方式」到底指什么——索引表格形态、`taskorder` 保鲜机制、`check_taskorder.sh` 的职责边界。
2. 就几个无法从需求文字直接推出的决策点向用户提问（文件名分隔符、是否接入 hook、是否改 CLAUDE.md、日志是否入库）。
3. 按决策落地目录结构、索引与首篇日志，并同步 `.gitignore` 与项目 `CLAUDE.md`。

## 三、实际做了什么

1. **摸清既有约定**：读取 `docs/meta.json`、`docs/design/index.md`、`docs/scripts/{increment_taskorder,check_taskorder}.sh` 与 `.claude/settings.local.json` 的 hook 挂载。确认 docs 侧的「相同方式」= 一个机器可解析的 `| 文件地址 | ... |` 表格索引 + `taskorder` 保鲜列 + Stop hook 走双向对账。当前 `taskorder = 12`。
2. **新建 `logs/index.md`**：沿用同一套表格与说明块写法，但按需求做了两处有意偏离——不设 `taskorder`/`只读` 列，且表格**倒排**（最新在最前）。表头为 `| 文件地址 | 文件名 | 简要内容 | 完成时间 |`。

5. **改项目 `CLAUDE.md`**：在「文档维护」之后新增「日志维护」一节，让后续任务的 agent 知道该约定。

## 四、遇到了什么问题

**问题 1：需求里定的文件名格式带冒号，在 macOS/APFS 上会踩坑。**
用户写的是 `yyyy-mm-dd_hh:mm:ss+主题`，但 `:` 在 macOS 文件名里会被 Finder 显示成 `/`，跨平台拷贝与部分工具链也容易出问题。

**问题 2：`logs/` 被 `.gitignore` 忽略，agent 日志会被静默排除在 git 之外。**
`.gitignore` 第 35 行是 `logs/`（无前导斜杠，匹配任意层级），意味着 `logs/` 与 `docs/logs/` 都会被忽略。同时 `src/`、`pom.xml` 中没有任何 logback/log4j 配置指向该目录，这条规则疑似历史遗留、并无实际用途。

**问题 3：日志索引是否也该维护 `taskorder`。**
若完全镜像 docs，每条日志都会因为「任务号落后」而被 `check_taskorder.sh` 持续报「可能过时」——但日志是追加型存档，这个语义并不成立。

## 五、如何解决的

三个问题都通过 `AskUserQuestion` 交用户决策后落地，未静默处理：

- **问题 1** → 用户选择用短横线替代冒号：`yyyy-mm-dd_hh-mm-ss_主题.md`。跨平台安全，排序行为与冒号版完全一致。
- **问题 2** → 用户选择放行 `logs/`、纳入版本控制，故从 `.gitignore` 中删掉那条用不上的 `logs/`。
- **问题 3** → 用户选择 `logs/` **暂不接入 hook**、不维护 `taskorder`。因此本索引不设 `taskorder` 列，`logs/index.md` 也被有意放在**仓库根**而非 `docs/` 下——后者会被 `check_taskorder.sh` 的 `docs/**/index.md` glob 扫到，因缺 `taskorder` 列而每次输出一行「跳过该索引」的噪音。<br>⚠️ **关于「放在仓库根」的处置已于任务 13 被推翻**（用户要求日志目录必须位于 `docs/` 下），详见第七节。
- 另经用户确认，在项目 `CLAUDE.md` 增加「日志维护」条款，使该约定对后续任务生效。
