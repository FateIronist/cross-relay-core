# 规则里的兜底从句会与设计意图冲突，让执行者「合规地做错事」

**首次踩到**：任务 12–18（症状持续多轮，任务 19 定位并修复）

## 现象

`docs/design/index.md` 中 5 个非只读条目的 `taskorder` 连续多轮卡在 `1`，而 `docs/design/scripts/check_index.sh` 每轮收尾都在报「落后于当前任务号」。agent 每轮都读到了这条提醒、也逐篇复核了文档，却始终没有去更新它。表面上像是"agent 遵从度不够"。

## 原因

规则文本与字段的设计意图**直接冲突**。`CLAUDE.md` 文档保鲜条原文：

> 过时则更新文档内容，并把该文档登记的 `taskorder` 拨到当前任务号；**确认仍准确则不动**（结束检查的持续提醒属预期）

而这个字段的设计意图是「**本轮 agent 已复核该文档、并确认与现有架构对齐**」的**凭证**——因此**每轮都必须更新**，哪怕内容一字未改。

于是"按字面执行"（复核 → 确认准确 → **不动**）恰好就是不该做的行为。更糟的是括号里那句「持续提醒属预期」，把"没做"**合法化成了"设计如此"**——一个自我解释的闭环，让偏差可以无限期存续而不被当成问题。

## 规避

- **规则里别写与设计意图冲突的兜底从句。**「什么都不做」这个分支必须有明确且正确的适用条件（本仓后来的写法是「只读条目除外」，而不是「内容准确则不动」）。
- **不要把长期告警解释成"预期"。** 一条持续存在的告警几乎总是**未完成的工作**，而不是"设计如此"。这是判断此类问题最快的启发式：如果一个提醒每次都在响、而你每次都打算忽略它，那么要么提醒错了，要么活儿没干。
- **修规则优先于加工具。** agent 若是在忠实执行一条错误规则，加脚本、加检查都修不好它——只会让错误更快地固化成事实。定位时应先问"他是按哪条字面执行的"，再去判断遵从度。

## 本仓实例

任务 19 把该条改写为「**无论内容是否改动，复核后都必须把该条目的 `taskorder` 拨到当前任务号**（登记「只读=是」的条目豁免）」，并同步修正了 `docs/design/index.md` 的说明块与 `check_index.sh` 的提醒文案。原先那句「持续提醒属预期」已从三处全部删除。
