# 索引表格单元格里不能出现裸竖线

**首次踩到**：任务 12

## 现象

各域 `index.md` 的登记表是**机器可解析**的：检查脚本按 `|` 切分每行、再按表头列名取值。因此只要某个单元格的内容里出现一个未转义的 `|`，那一行的列数就会多出一列，字段整体错位——轻则该行解析出的路径是错的，重则脚本静默跳过该索引（脚本遇到列数异常会"跳过"而非报错）。

## 原因

表格解析是纯粹的**按分隔符切分**，不理解 markdown 转义语义。写文档时习惯性用 `|` 表示"或"（如 `A | B`），在正文里没问题，在表格单元格里就是结构性破坏。

## 规避

- 单元格内需要表达"或"时，改用顿号、斜杠或 `、`，不要用裸 `|`。
- 必须在单元格内保留字面竖线时，写 `\|`（是否被解析方识别需自行确认——本仓的脚本不处理转义，故实际约定是**一律不用**）。
- 表格里也不要写 `\n` 之类的换行符，一行一个登记项。

## 本仓实例

各域 `index.md` 的说明块（blockquote）可以随意写 `|`，因为它不以 `|` 开头、不会被当作表格行；但**表格行内**一律避免。可以用正则 `^\s*\|.*\|\s*$` 快速自查哪些行会被当作表格行。

### 再次踩到（任务 17，同一轮内）

本条目**在写下它的同一轮里就踩了它自己**：`docs/pitfalls/index.md` 中登记本文件的那一行，其「简要内容」写成了「按 `|` 切分解析……一律不用 `|`」——单元格里的两个裸竖线使该行解析出 7 列而非表头的 5 列。

危害是**分级的**，这也是它值得单独记一条的原因：

- 若错位发生在首个单元格**之前**，「文件地址」列会被读成错误内容，该文件被判「缺少索引」；
- 若错位发生在首个单元格**之后**（本次即如此），路径仍能正确读出，检查脚本**不会报错**——但若解析方要读 `taskorder` 等靠后的列，就会取到错误的值。属于**静默错误**；
- 现有三个域的检查脚本都只是对坏行「跳过」或「读错」，**没有任何一个会主动报告"列数异常"**。

因此自查不能靠检查脚本兜底，得在写完表格后用"列数是否等于表头列数"独立核对一遍。
