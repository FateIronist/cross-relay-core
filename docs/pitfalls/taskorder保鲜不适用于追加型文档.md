# `taskorder` 保鲜语义不能照搬到追加型文档

**首次踩到**：任务 13 / 14

## 现象

`taskorder` 保鲜的规则是"登记值必须等于当前任务号，否则可能是过时的、需要复核"。它隐含一个前提：**每轮任务都应该动这份文档**。对设计文档这成立——架构变了文档就得跟着改。

但对**追加型存档**（日志、踩坑记录）不成立：写于任务 12 的日志，在任务 13、14、15 都不该被判定为"过时"。硬套的结果是每一行历史记录永远处于"落后"状态，检查输出被噪音淹没，真正的信号反而看不见。

## 原因

"保鲜"和"追加"是两种正交的文档生命周期：

- **保鲜型**：内容是对现状的描述 → 现状变了就该重写 → 落后 = 可疑；
- **追加型**：内容是历史事实的记录 → 一旦写下就不再改变 → 落后 = 正常。

把同一套校验套在两种生命周期上，必然对其中一种失效。

## 规避

**按生命周期选择校验口径**，而不是按文档格式：

- 保鲜型 → 逐行校验 `taskorder == 当前`；
- 追加型 → **只校验"最新一条"**。对倒排索引即首行，语义是"最新记录须由当前任务产生"；其余历史行完全不校验。
- 有些域可能两者都不是（如踩坑记录，不是每轮都有），那就**干脆不校验** `taskorder`，只保留索引↔磁盘对账。

关键是把"列"和"校验规则"解耦：`taskorder` 列可以照样记录（供追溯"这事发生在哪一轮"），但不代表它必须被校验。

## 本仓实例

`docs/logs/` 用"只校验倒排首行"；`docs/pitfalls/` 连首行都不校验（踩坑不是每轮都有，不能强制），仅做索引↔磁盘对账。三个域的检查脚本因此各不相同，这是**有意的差异化**，不是不一致。
